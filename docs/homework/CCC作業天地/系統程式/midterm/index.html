Section 1 · 系統背景

問題動機

現有 AI 程式碼生成工具（如 Copilot、Codex）在面對複雜、多領域的軟體系統時，常有以下問題：
  • 單一 AI prompt 無法同時處理：前端、後端、資料庫、認證等多面向任務
  • 推理過程不透明：難以理解 AI 為何做出某個分工決策
  • 缺乏顯性的需求收斂：還沒確認需求就先實作，方向錯誤後難以修正
  • 無法表達「我的意圖是什麼」：只能寫規格，無法讓 AI 理解背後的意圖

解決方向：Evolution

Evolution OS 是一個以 意圖驅動（Intent-Driven）為核心的 AI 推理/協作工具。
Input 任務描述（自然語言）
Analyze 分析問題的複雜度、領域多樣性、推理分支數
Dispatch 決定 Solo 或 Fork 模式
Plan 輸出完整的分工 Manifest
Execute 根據 Manifest 調度 AI 節點執行
核心理念
「能夠給 AI 更好輸入的軟體」，而不是「寫代碼的軟體」。最終目標是讓 AI 理解人類的意圖，而不只是執行指令。

Planner Stage Flow（核心流程）

輸入：task description
   │
   ├─▶ S1: 確認需求（questions[]）
   │       └─ 輸出：待確認問題清單
   │
   ├─▶ S2: 分析問題
   │       └─ ComplexityMetrics.estimate_from_task()
   │           ├─ reasoning_branches（推理分支數）
   │           ├─ domain_diversity（領域多樣性）
   │           └─ context_complexity（語境複雜度）
   │
   └─▶ S3: 規劃派工
           └─ WorkMode.decide(metrics)
               ├─ Solo: branches ≤ 2 AND diversity ≤ 1 AND complexity ≤ 0.6
               └─ Fork: branches > 2 OR diversity > 1 OR complexity > 0.6

Section 5 · OS Kernel 核心（v0.3.0）

核心元件

kernel/
├── mod.rs              # Kernel — syscall() 單一進場點
├── process.rs          # Process / ProcessState / Pid（含 Debug impl）
├── mailbox.rs          # Mailbox（FIFO 訊息佇列）

System Call 介面

pub enum SysCallKind {
    Spawn(Box<dyn SystemProcess>),    // 創建新行程
    Send { to: Pid, msg: String },   // 發送訊息
    Receive,                          // 接收訊息（blocking）
    Wait(Pid),                        // 等待指定行程結束
    Exit,                             // 行程結束
}

Section 9 · 設計原則

核心設計原則

  • 問題未確認不實作：S1 强制產出問題清單，防止方向錯誤
  • 複雜度驅動分工：分工依據是「推理複雜度」，不是「任務數量」
  • 邏輯上的遞迴：Planner 的優化輸出 → 更好的下次輸入結構
  • 可驗證的決策：每個分工決策都有可讀的 rationale
